# ADR-001：本地存储采用「单 JSON 文档 + 原子写 + 三代轮转」

- 状态：已采纳（Flutter 版 v1）
- 日期：2026-11-08
- 相关：ADR-002（许可）、`src/data/persistence.ts`、`src/data/backup.ts`

## 背景

React 版把数据拆成 5 个 localStorage 键（工时 / 账目 / 自定义分类 / 工作 / 预算），每个键各自维护 `key`、`key.bak`、`key.bak.1` 三代。这套做法解决了两件事：单键损坏可回退、写入失败不破坏主数据。

Flutter 端没有 localStorage。可选方案有三类：关系库（drift/sqflite）、键值库（Hive/Isar）、文件文档。

约束条件：

1. 迁移必须无损，且迁移通道只能是 JSON 备份 v4（`src/data/types.ts:59-68`）。
2. 导出、备份、存储三者的数据形状越接近越好——任何「存储格式 ≠ 备份格式」的设计都会引入第二次序列化，多一处偏差来源。
3. 数据量极小：每天最多 1 条工时 + 若干账目，一年几百条，整文档几十 KB。
4. 金额零偏差是硬要求，存储层不能做任何隐式类型转换。

## 决策

**存储格式就是备份 v4 的整文档**，落盘为一个文件：

```
<appSupportDir>/my-hours.json        # 主文档
<appSupportDir>/my-hours.json.bak    # 上一代
<appSupportDir>/my-hours.json.bak.1  # 上上代
```

文档结构（与备份文件同构，`version: 4`）：

```json
{
  "app": "my-hours",
  "version": 4,
  "exportedAt": "<ISO8601>",
  "records": [],
  "entries": [],
  "customCategories": [],
  "workProfiles": [],
  "budgetTargets": { "monthlyExpenseBudget": 0, "monthlyIncomeGoal": 0 }
}
```

写入流程：

1. 序列化整文档到内存（UTF-8，不压缩——可读性优先于体积）。
2. 写 `my-hours.json.tmp`（`File.writeAsStringSync(flush: true)`，把数据交给 OS 并请求落盘；Dart 不暴露独立的 `fsync`，断电窗口由 `.tmp` + `rename` 兜住）。
3. 若主文件存在**且本次会话的主文件可信**：`my-hours.json` → `my-hours.json.bak`，`my-hours.json.bak` → `my-hours.json.bak.1`（后写覆盖前写，任一步失败不阻断主写入）。
   - 「可信」= 本次启动没有从 `.bak` / `.bak.1` 回退。回退说明主文件已损坏，此时**不得**把坏主文件轮转成 `.bak`——否则好备份会被挤到 `.bak.1`，再写一次就三代全坏。
4. `rename(tmp → my-hours.json)`（同目录，POSIX/Android 上是原子替换）。
5. 失败只记日志，不抛给 UI；下一次写重试。

读取流程：主文档 → `.bak` → `.bak.1`，第一个**解析成功且通过归一化**的胜出；三代都坏时返回 `corrupted`，由启动层显示「数据损坏」提示并保留现场（不静默当成空数据，也不做自动迁移）。

启动对账：读取后执行一次 `syncWageEntries`；**只有结果引用变化才回写**（对齐 `src/data/wageEntries.ts:72-111` 的 `changed` 短路），避免每次冷启动把三代备份拍成同一份内容。

## 后果

正面：

- 迁移 = 复制文件；导出 = 同一份字节；导入 = 同一套 parse 与 normalize。三处不会漂移。
- 没有 codegen、没有 schema 迁移脚本、没有 ORM 行为差异。
- 备份文件可以被用户直接打开检查（排障成本低）。

负面（必须接受）：

- **粒度变化**：从「每键独立三代」变成「整文档三代」。单个字段写坏时无法只回退那一块；但整文档三代在单文件写入下已覆盖真实故障模式（写到一半断电）。
- 每次保存全量重写：几十 KB × 每天几次，可忽略。
- 未来若要按条件查询历史（例如跨年搜索），需要全量加载到内存——当前数据量下可接受；若数据量增长到十万级，再评估引入索引层。

## 被否方案

| 方案 | 否决理由 |
|---|---|
| drift / SQLite | 存储格式与备份 v4 脱钩，需要双向映射；引入 codegen 与迁移脚本；迁移工作量翻倍，而收益（查询性能）在当前数据量下为零 |
| Hive / Isar | 二进制格式不可读，排障与手工修复困难；同样与备份格式脱钩 |
| 继续用「每键一个文件」 | 5 个文件 × 3 代 = 15 次写入，原子性无法跨文件保证；崩溃时可能得到「工时是新的、账目是旧的」这种不一致状态，而工资对账依赖两者一致 |

## 验收

- 用真实 v4 备份导入后，月工时 / 月工资 / 待结算 / 已结算 / 账目结余五项与 React 版逐项相等。
- 人为截断主文档 → 自动回退 `.bak`，数据完整。
- 主文档与 `.bak` 都损坏 → 启动显示「数据损坏」提示，不显示「0 条记录」的空态。
- 从 `.bak` 回退后再保存，`.bak` 仍是可读的好数据（坏主文件不会被轮转进备份）。
- 连续 30 次保存后，`.bak` 与 `.bak.1` 内容互不相同（证明轮转生效）。
